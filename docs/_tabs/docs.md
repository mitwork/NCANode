[https://github.com/malikzh/NCANode/releases](https://github.com/malikzh/NCANode/releases)

## Запуск NCANode

Для запуска необходимо выполнить команду:

```bash
java -jar NCANode-3.0.0.jar
```

### Запуск в Docker

У NCANode есть образ в Docker Hub, и запустить его можно следующим образом:

```bash
docker volume create ncanode_cache
docker run -p 14579:14579 -v ncanode_cache:/app/cache -d malikzh/ncanode
```

## Настройки

В отличие, от версий 2.x, 1.x, теперь NCANode настраивается при помощи переменных окружения (os env).

Эти переменные окружения подставляются в конфигурацию в этом файле: [https://github.com/malikzh/NCANode/blob/master/src/main/resources/application.yml](https://github.com/malikzh/NCANode/blob/master/src/main/resources/application.yml)

### Список переменных окружения

* `NCANODE_PORT` - Порт (по умолчанию 14579)
* `NCANODE_DEBUG` - режим отладки (по умолчанию отключен)
* `NCANODE_CACHE_DIR` - путь к папке с кэшем (по умолчанию ./cache)
* `NCANODE_CRL_ENABLED` - поддержка CRL (по умолчанию включена)
* `NCANODE_CRL_TTL` - Время жизни CRL в кэше (по умолчанию 1440 минут)
* `NCANODE_CRL_URL` - URL'ы откуда скачивать списки CRL. По умолчанию они берутся из:
  * https://crl.pki.gov.kz/nca_gost_2022.crl
  * https://crl.pki.gov.kz/nca_rsa_2022.crl
* `NCANODE_CRL_DELTA_URL` - URL'ы дельта версий CRL. *Они обычно обновляются чаще чем основные*. По умолчанию:
  * https://crl.pki.gov.kz/nca_d_gost_2022.crl
  * https://crl.pki.gov.kz/nca_d_rsa_2022.crl
* `NCANODE_CRL_DELTA_TTL` - Время жизни Delta-CRL в кэше (по умолчанию 1440 минут)
* `NCANODE_CRL_STRICT` - Строгий режим CRL (SSRF-защита). Если `true`, on-demand загрузка CRL по адресу из проверяемого сертификата (`cRLDistributionPoints`) отключена — используются только сконфигурированные CRL (`NCANODE_CRL_URL` / `NCANODE_CA_CRL_URL`). Так сертификат злоумышленника не заставит сервер обратиться к произвольному (внутреннему) хосту. По умолчанию: `false`. Независимо от флага, адреса из сертификата, указывающие на loopback/link-local (напр. 169.254.169.254), всегда блокируются.
* `NCANODE_CRL_MAX_SIZE_MB` - Потолок размера скачиваемого CRL в мегабайтах (по умолчанию: 64). Загрузка обрывается, как только тело ответа превысило потолок, а если сервер прислал `Content-Length` — ещё до чтения тела; недокачанный файл не сохраняется, прежний CRL на диске остаётся рабочим. Ограничение важно в нестрогом режиме (см. `NCANODE_CRL_STRICT`), где адрес CRL берётся из проверяемого сертификата. Значение `0` снимает ограничение. Для сравнения: боевой `nca_gost_2022.crl` — около 20 МБ.
* `NCANODE_CRL_ONDEMAND_MAX` - Максимум CRL-файлов, скачанных по адресу из сертификата (`cRLDistributionPoints`), которые хранятся в кэше (по умолчанию: 64). При превышении вытесняются реже всего использованные — вместе с их индексами. «Использованный» — тот, что реально пригодился при проверке сертификата; никому не пригодившиеся уходят первыми. Значение `0` снимает ограничение. На CRL из `NCANODE_CRL_URL` / `NCANODE_CA_CRL_URL` не влияет.
* `NCANODE_HTTP_CLIENT_CONNECT_TIMEOUT` - Таймаут установления TCP-соединения для исходящих HTTP-запросов в секундах (по умолчанию: 5)
* `NCANODE_HTTP_CLIENT_REQUEST_TIMEOUT` - Общий бюджет на исходящий HTTP-запрос (включая отдачу тела) в секундах. Влияет на скачивание крупных CRL (по умолчанию: 30)
* `NCANODE_HTTP_CLIENT_MAX_RESPONSE_KB` - Потолок размера ответа в килобайтах для OCSP, TSP и загрузки CA-сертификатов (по умолчанию: 1024). Все три обмена измеряются единицами килобайт, так что мегабайт — запас в десятки раз. Ограничение важно потому, что адрес OCSP-респондера в нестрогом режиме (см. `NCANODE_OCSP_STRICT`) берётся из расширения AIA проверяемого сертификата, а ответ читается в память. Превышение трактуется как «ответа не было»: для OCSP это `UNAVAILABLE`, то есть допускается переход на свежий CRL. Значение `0` снимает ограничение. На CRL не влияет — у них свой потолок `NCANODE_CRL_MAX_SIZE_MB`.
* `NCANODE_HTTP_CLIENT_USER_AGENT` - HTTP заголовок User-Agent у клиента
* `NCANODE_PROXY_URL` - Прокси для HTTP-клиента. Через этот прокси будут происходить все запросы из NCANode.
* `NCANODE_PROXY_USERNAME` - Имя пользователя в прокси
* `NCANODE_PROXY_PASSWORD` - Пароль прокси
* `NCANODE_OCSP_URL` - OCSP-сервер куда будут происходить запросы. По умолчанию: http://ocsp.pki.gov.kz/
* `NCANODE_OCSP_STRICT` - Строгий режим OCSP (SSRF-защита). Если `true`, OCSP-проверка игнорирует адрес responder'а из AIA сертификата и ходит только на сконфигурированный `NCANODE_OCSP_URL`. По умолчанию: `false` (AIA-first, config-fallback).
* `NCANODE_CA_URL` - URL-ы корневых сертификатов. Они скачиваются автоматически при запуске NCANode. По умолчанию:
  * https://pki.gov.kz/cert/nca_rsa.crt
  * https://pki.gov.kz/cert/nca_gost.crt
  * https://pki.gov.kz/cert/root_gost_2022.cer
  * https://pki.gov.kz/cert/nca_gost_2022.cer
* `NCANODE_CA_TTL` - Время жизни корневых сертификатов CA (по умолчанию 1440 минут)
* `NCANODE_CA_CRL_ENABLED` - Проверка корневых сертификатов на отозванность. Если сертификат отозван, NCANode попробует его заново скачать. (По умолчанию: true)
* `NCANODE_CA_CRL_TTL` - Время жизни для CRL корневых сертификатов (по умолчанию 1440 минут)
* `NCANODE_CA_CRL_URL` - Список URL-ов откуда скачивать CRL. По умолчанию:
  * http://crl.root.gov.kz/gost.crl
  * http://crl.root.gov.kz/rsa.crl
  * http://crl.root.gov.kz/gost2015_2022.crl
  * http://crl.root.gov.kz/rsa2020.crl
* `NCANODE_XADES_EXCLUDE_SIGNATURES` - Ссылка XAdES-подписи исключает из покрытия **все** подписи документа, а не только свою. Нужно, если по документу идут несколько подписантов: иначе подпись, добавленная позже, ломает предыдущую для тех проверяющих, которые не восстанавливают документ на момент подписания. Меняет формат выпускаемых подписей (XPath вместо `enveloped-signature`), поэтому по умолчанию: `false`. Подробнее — в разделе про AdES.
* `NCANODE_TSP_URL` - URL TSP-сервера. По умолчанию: http://tsp.pki.gov.kz/
* `NCANODE_TSP_RETRIES` - Количество неудачных попыток обращения к TSP-серверу, по умолчанию: 3

## Проверка отзыва сертификатов (OCSP / CRL)

Проверка отзыва — **opt-in**: если `revocationCheck` в запросе не указан, отзыв
**не проверяется**, и отозванный (но в остальном валидный) сертификат пройдёт
как `valid: true`. В этом случае в логах пишется предупреждение (WARN). Чтобы
включить проверку, передайте `revocationCheck: ["OCSP", "CRL"]`.

Если в запросе верификации указаны обе проверки (`revocationCheck: ["OCSP", "CRL"]`),
выполняются **обе**, и отзыв, найденный любым из каналов, делает сертификат
невалидным. Особые случаи:

* **OCSP недоступен по сети** (таймаут, connection refused, ответ не парсится) —
  верификация автоматически деградирует на CRL: сертификат считается валидным,
  если свежий (не истёкший по `nextUpdate`) CRL его издателя не содержит его
  серийника. Это стандартная модель OCSP-preferred + CRL-fallback (RFC 5280 §6.3).
  В `revocations[]` такой канал помечается `"result": "UNAVAILABLE"`.
* **OCSP ответил, но ответу нельзя верить** (несовпадение nonce, битая подпись
  ответа, статус unknown) — сертификат невалиден независимо от CRL
  (`"result": "UNKNOWN"`, fail-closed).
* **CRL издателя нет в кэше** (CA не публикует CRL, или он не сконфигурирован) —
  CRL-канал помечается `"result": "UNAVAILABLE"`; это не мешает валидности при
  живом OCSP, но такой CRL не может служить fallback-источником.

CRL-проверка учитывает delta-CRL по RFC 5280 §5.2.4: если для издателя есть
и полный (base), и применимая к нему delta (`NCANODE_CRL_DELTA_URL`), они
объединяются — delta авторитетна для изменений после base (включая снятие
отзыва `removeFromCRL`). Delta обновляется чаще (меньший `nextUpdate`),
поэтому картина отзывов, а значит и свежесть CRL-fallback'а, актуальнее,
чем по одному полному CRL.

Каждый элемент `revocations[]` в ответе несёт поле `result`
(`ACTIVE` / `REVOKED` / `UNKNOWN` / `UNAVAILABLE`). Клиент, которому нужна
строгая политика «оба канала обязаны ответить», может реализовать её сам:
`valid && revocations.none { result == "UNAVAILABLE" }`.

## Подписи AdES (CAdES / XAdES / PAdES)

Помимо привычных `/cms`, `/xml` и `/pdf` есть три семейства эндпойнтов,
выпускающих и проверяющих подписи по профилям ETSI — тем самым, что понимает
обновлённый NCALayer:

| Формат | Эндпойнты | Что подписывает |
|---|---|---|
| CAdES | `/cades/sign`, `/cades/verify` | произвольные данные (attached или detached) |
| XAdES | `/xades/sign`, `/xades/verify` | XML-документ |
| PAdES | `/pades/sign`, `/pades/verify` | PDF-документ |

Старые эндпойнты никуда не делись и работают как прежде — переходить на новые
нужно только если требуется совместимость с AdES-уровнями.

### Уровни

Уровень задаётся полем `level` при подписании. Уровни нарастающие: LTA включает
в себя LT, тот — T, тот — B.

| Уровень | Что добавляет | Что для этого нужно |
|---|---|---|
| `B` | привязку подписи к сертификату и алгоритмам | ничего сверх ключа |
| `T` | метку доверенного времени на подпись | доступный TSA |
| `LT` | вшитые цепочку и данные об отзыве | доступные OCSP или CRL на момент подписи |
| `LTA` | архивную метку поверх всего перечисленного | доступный TSA |

Смысл `LT` в том, чтобы подпись проверялась без обращения к сети и после
истечения сертификата. Поэтому если данных об отзыве для какого-то звена
цепочки получить не удалось, подпись уровня LT **не выпускается** — иначе она
выглядела бы долгоживущей, не будучи таковой.

### `level` и `verifiedLevel` в ответе проверки

Это разные вещи, и путать их не стоит:

* **`level`** — что подпись о себе **заявляет**: какие структуры в ней нашлись;
* **`verifiedLevel`** — до чего уровень **подтверждён** проверкой.

Документ с архивной меткой заявит `level: LTA`, но если метку проверить не
удалось, `verifiedLevel` окажется `LT` или ниже. Практическое следствие: без
`revocationCheck` в запросе `verifiedLevel` **не поднимется выше `T`** —
вшитый материал никто не смотрел, и объявить уровень LT было бы неправдой.
Хотите подтверждения LT/LTA — передавайте `revocationCheck: ["OCSP", "CRL"]`.

При проверке источник данных об отзыве выбирается не по принципу «вшитый или
живой», а по тому, **чей интервал действия покрывает проверяемый момент**
(им считается время метки, если она есть). Поэтому старая подпись проверяется
по вшитому материалу, а свежая без метки — живым запросом, и отдельного
переключателя для этого не нужно.

### Несколько подписантов

Все три эндпойнта принимают массив `signers` — так подписывают, когда все ключи
доступны сразу.

Когда подписанты идут по очереди (первый подписал, документ ушёл дальше, второй
подписывает через день), документ возвращают на подпись ещё раз:

* **XAdES** и **PAdES** — отправьте уже подписанный документ обратно в
  `/xades/sign` или `/pades/sign`. Добавится ещё одна подпись, предыдущие
  останутся действительными.
* **CAdES** — для этого есть `PATCH /cades/sign`: в нём вместо `data` передаётся
  готовый `cms` (а для отсоединённой подписи — и `data` тоже). Прежние
  подписанты, их метки времени и вшитый материал сохраняются, новый получает
  полный набор AdES-атрибутов. Поле `level` в этом запросе относится к новому
  подписанту, а `level` в ответе — к документу целиком, то есть к слабейшей из
  подписей.

Не используйте для AdES-контейнеров `PATCH /cms/sign`: он добавит подписанта без
AdES-атрибутов и потеряет вшитые данные об отзыве — подпись останется валидной,
но перестанет быть долгоживущей.

Порядок в PDF значим: правка документа между подписями сломает предыдущую.
Дописывать между подписаниями можно только материал проверки и новые подписи.

#### Несколько подписантов в XAdES

По умолчанию подпись вкладывается в документ обычным способом
(`enveloped-signature`), при котором из её покрытия исключается только она
сама. Следующая подпись попадает в покрытие предыдущей, и предыдущая
становится недействительной для всех, кто не восстанавливает документ на
момент подписания. NCANode восстанавливает, поэтому свои документы проверяет
верно; сторонние проверяющие — нет.

Если по документу идут несколько подписантов, включите
`NCANODE_XADES_EXCLUDE_SIGNATURES=true`. Тогда ссылка исключает из покрытия
все подписи сразу, и документ проверяется кем угодно, сколько бы подписей в
нём ни было. Цена — трансформ XPath вместо `enveloped-signature`: первый в
реализациях XMLDSig необязателен, поэтому по умолчанию режим выключен. Флаг
влияет только на выпуск новых подписей; проверка принимает оба варианта
всегда.

Само NCALayer документ с существующей подписью повторно не подписывает —
отвечает, что это сделает предыдущую подпись недействительной. Его валидатор
при этом принимает документы, выпущенные в режиме
`NCANODE_XADES_EXCLUDE_SIGNATURES`, — включая уровень LTA.

### Особенности форматов

* **XAdES** — два размещения: `ENVELOPED` (подпись вкладывается в документ,
  по умолчанию) и `ENVELOPING` (документ вкладывается в подпись — в NCALayer
  это «присоединённая, содержимое внутри»; поддерживается один подписант,
  корень у документа один). `DETACHED` отклоняется явной ошибкой. Проверка
  принимает оба размещения, в том числе подписи, созданные NCALayer.
* **PAdES** — каждая подпись добавляется отдельной ревизией файла, так что
  предыдущие не разрушаются. Видимое представление задаётся полем
  `visibleSignature.template` — это PDF в Base64, в котором уже нарисовано всё
  нужное, включая логотип; сервис лишь размещает его на указанной странице
  (`page`, нумерация с единицы). Такой же контракт у NCALayer.
* **Материал для проверки** (уровень LT) кладётся туда же, куда его кладёт
  НУЦ: в CMS — в сам `SignedData`, в PDF — в словарь `/DSS`.

### Повышение уровня готовой подписи

`/cades/extend`, `/xades/extend`, `/pades/extend` поднимают уровень уже
подписанного документа, **не требуя ключа**: всё, что добавляют уровни выше
`B`, надстраивается поверх подписи, ничего не подписывая заново. Запрос —
сам документ и требуемый `level` (для отсоединённой CAdES ещё и `data`).

Зачем это нужно: NCALayer в браузере отдаёт сайту только обычную CMS- или
XML-подпись, уровни `LT` и `LTA` через его веб-сокет недоступны. Поэтому
типичная схема — клиент подписывает в браузере, а сервер доводит подпись до
долгоживущего уровня.

Что при этом происходит: добирается недостающее, а уже имеющееся не трогается
— чужую метку времени нельзя ни заменить, ни продублировать. Уровень ниже
достигнутого (или равный ему) — ошибка `400`: снять уровень нельзя, а
«повышение» до текущего молча ничего бы не сделало.

Ограничение PAdES: добрать можно `LT` и `LTA` — они добавляются отдельными
ревизиями файла. Уровень `T` так не добавить, метка подписи лежит внутри самой
подписи, в области фиксированного размера.

### Массовые операции

У всех трёх семейств есть batch-варианты: `/cades/sign/batch`,
`/cades/verify/batch` и так далее. Подписант **и уровень** общие на весь пакет,
а результат у каждого элемента свой: ответ приходит с кодом 200, если пакет
обработан до конца, а получилось ли с конкретным документом — смотрите в
`results[i].status`. Ошибка в одном элементе не роняет остальные.

### Совместимость с NCALayer

Подписи, созданные NCALayer, проверяются всеми тремя эндпойнтами — включая
уровни LT и LTA.

Обратное ограничение стоит знать, если вы отлаживаетесь на **тестовых** ключах
НУЦ: сам NCALayer выпускает такими ключами только уровни B и T, а на LT и выше
отвечает ошибкой построения цепочки — ограничение на его стороне. На боевых
ключах все четыре уровня работают.

## Запуск с переменными окружения

Например, мы хотим изменить порт и включить отладку. То мы запускаем NCANode так:

```bash
NCANODE_PORT=8080 NCANODE_DEBUG=true java -jar ./NCANode.jar
```

Для Docker необходимо использовать параметр `-e`. Например:

```bash
docker run -p 8080:8080 -v ncanode_cache:/app/cache -e NCANODE_PORT=8080 -e NCANODE_DEBUG=true -d malikzh/ncanode
```

## Запросы к NCANode

После запуска NCANode можете перейти по адресу:

[http://localhost:14579/actuator/health](http://localhost:14579/actuator/health)

В ответ придет что-то вроде:

```
{"status":"UP"}
```

### Важно знать
  
Обратите внимание, что ключи, CMS, и данные в CMS передаются в формате **Base64**. Это описано в API Reference.

И в каждом запросе не забывайте передавать заголовок `Content-Type: application/json`.
